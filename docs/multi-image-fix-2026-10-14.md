# 多图漏解析与“0 风险”误导修复

## 已观察到的问题

用户同时上传“大连→葫芦岛”和“大连→秦皇岛”车票，两段均为 2026-10-26 09:54 出发。页面与用户提供的 TripGraph 只有秦皇岛一段，金额也只计 112 元，因此风险引擎没有收到第二段，显示 0 风险。

此前手动补齐两段后的 75 分规则测试只说明规则能识别重叠，不代表真实图片解析已修复。没有保存原请求响应，不能据此断言模型当时为何漏读；可以确认旧代码没有逐图覆盖校验。

## 修改

1. 多图请求仍为一次批量请求，按序为图片加 `image_index` 标签；单图接口保持兼容。
2. 要求返回每张图独立的行程草稿，不让模型提前合并、去重或处理冲突。每张图都必须有对应结果，缺少编号、重复编号、漏项或未识别到事件时不接受完整解析。
3. 程序合并所有图片中的事件，重编号，重绑定前置事件和受保护引用，重映射字段置信度并保留图片来源编号。时间相同不能成为删除依据；不同文件即使行程字段相似也不自动删除。完全相同的重复文件仅在整个事件列表事实一致时复用；同一图中的多条订单不被压缩为一条。
4. 缺失日期、价格或地点继续进入人工补全，不删除对应车票。多图预算/人数等全局信息不一致时留空，要求用户确认。
5. 页面展示上传图片与初始行程序号的对应关系。编号覆盖不等于所有文字都读对，不能替代人工核对。
6. 有照片预览但无逐图覆盖记录的旧多图历史标为待复核；可以查看原数据，但不复用其旧“0 风险”或“无需 Plan B”结论。原图有效则重新解析；已过期则需重传，不允许只靠低清预览恢复完整性。

## 费用与验证边界

没有新增逐张模型调用，没有提高配额或输出上限。一次点击仍使用一批图片的请求；沿用既有最多两次的结构修复策略，第二次仅在第一次不合格时发生，两次均失败则明确停止，模型服务仍可能计费。

新增回归测试通过模拟 HTTP 响应验证：实际组装两张图片的请求、逐图结果、合并、补全确认、风险检查及本地 Plan B；模拟旧版只返回一段、漏图、图片无法识别、重复文件、缺失日期和旧历史保护。测试不调用付费模型，不按文件名称特殊处理。

这不是新的真实百炼视觉识别验收，也不承诺任何模型不会错读或复制错误内容。真实原图的最终效果需要部署后重新解析核对：应同时显示葫芦岛和秦皇岛两段，已知金额 205 元；总预算 300 元时，本地规则应检出一个时间重叠风险。若模型未按要求返回完整结果，应指出未核齐并停止，而不是静默报告 0 风险。
