## 旅行场景与目标用户

作品面向已订好部分交通、酒店或活动，但需要检查整段行程能否顺利执行的自由行、多段铁路出行和家庭旅行用户。对于同行老人、儿童或有步行限制的旅客，用户也可以补充人数与体力约束，检查安排是否过于紧张。

常见痛点是：订单分别保存在 12306、酒店和活动页面里，单张订单正确，并不代表整趟行程合理。用户需要自己核对跨站交通时间、同一时段的重复安排、住宿日期、总费用和每日步行负担；普通问答还可能给出没有来源的价格与候选。

途证哨从真实截图切入，不要求用户先改写为固定模板，也不要求重新设计整趟旅行。其重点是理解已有安排、发现问题、保护不希望变动的行程，再帮助用户选择下一步。产品定位是“已有行程的核对与辅助决策”，不是通用攻略生成器，也不是售票或代订平台。

## 我做了什么

### 核心流程

1. 导入 1–5 张车票、机票、酒店订单或行程截图，将识别结果整理为行程草稿。多图仍使用批量请求，但要求模型逐图返回，程序校验覆盖后再合并；时间相同、目的地不同的两张票不能被当作重复内容删除。漏图则停止构建并提示，不用残缺行程报告“0 风险”。
2. 对缺失的预算、日期、地点、人数等必要信息提示人工补全；展示字段置信度与中文解释，允许校对结构化行程。已取消或退票订单明确提示失效，不作为有效计划直接构建。
3. 用户确认后构建 TripGraph，展示时间线，并检查时间重叠、衔接缓冲、住宿日期、预算与体力等规则；有实际天气证据时检查其覆盖范围。
4. 生成 Plan B：先尝试对现有冲突做局部调整；需要新候选时，通过百炼 Managed Agent 编排高德 MCP 和 FlyAI 工具查询，再对候选来源、价格、约束及风险变化进行校验。
5. 支持针对当前行程提问、自动切换历史会话，以及导出 TripGraph JSON 和日历 ICS。

### 核心创新

- **从“生成攻略”转向“核验已有行程”**：面向已持有零散订单的用户，解决旅行执行前的核对问题，而不只是生成一段推荐文本。
- **可计算的旅行数字孪生**：TripGraph 统一表达行程事件、时间、位置、费用、依赖与受保护项目；用户修改后可以重新检查。
- **大模型与规则分工**：模型负责截图理解、工具编排和解释，显式规则负责风险判断；识别置信度与行程风险分开呈现。
- **完整性先于风险结论**：保留图片与事件的对应关系，先检查是否漏图，再检查事件结构与约束，最后计算风险；字段置信度高不代表所有图片都已识别，更不代表整个行程合理。
- **先验证，再推荐**：候选必须有本次工具查询证据与来源链接，不能只凭模型说法。局部调整方案通过结构、引用、预算与风险回放复检，并展示调整前后的差异。
- **真实使用中的边界与成本控制**：缺失信息要求补全，核验失败或证据精度不足明确说明；示例、缓存和实时调用分开标注，配合每日额度与重复问题缓存控制成本。

## 百炼使用说明（必填）

- 百炼能力 / 模型：百炼位于作品的运行时链路，实际用于视觉解析、自由问答、Managed Agent 工具编排，不仅用于辅助写代码。代码中的文本、视觉模型默认均为 `qwen3.7-flash`，可通过部署环境变量覆盖；Managed Agent 的模型或智能模式由百炼控制台独立配置，不把历史证据中的 `qwen3.8-flash` 写成当前固定模型。
- 调用方式：Python 通过百炼兼容 Chat Completions API 执行截图解析与自由问答，通过 Managed Agents API 发起独立会话和读取工具事件。
- 使用环节与输入输出：
  - 截图解析：输入上传图片和结构约束，输出行程草稿、字段置信度和缺失信息提示，经过人工补全确认后构建 TripGraph。
  - 自由问答：输入当前行程、风险和已验证候选，输出简短解释；不虚构未知价格、库存、天气或退改政策。
  - 实时核验与候选查询：输入当前 TripGraph 和待处理风险，Managed Agent 按需调用高德 MCP 与 FlyAI，输出路线、天气或候选证据；应用再执行确定性校验。
- Skill 名称：飞猪官方 FlyAI 旅行 Skill/CLI；仓库保留其适配版本 `triptwin-flyai` 和原始授权说明。飞猪查询能力属于官方工具，本项目原创部分是 TripGraph、风险引擎、受约束校验与用户交互，不将上游工具宣称为原创。
- 其他工具 / 技术栈：Python、Gradio、Pydantic、SQLite、高德地图 MCP、FlyAI CLI、GitHub Actions、ModelScope 创空间。

### 评委快速体验

1. 打开在线应用，在第 1 步展开“行程功能示例”，选择“行程冲突异常示例”。
2. 点击第 2 步“解析行程截图”，查看时间线和置信度；核对第 3 段车次被遮挡的说明并确认低置信字段。
3. 点击“检查风险”，查看两段行程同一时刻出发的证据。
4. 点击“生成 Plan B”，比较两个局部方案；选择一个并“应用到当前行程”，查看更新后的时间线与风险。
5. 新建独立会话，再选择原历史会话，检查已保存结果恢复；可导出 JSON 和 ICS。

该快速体验使用本地功能示例，不产生新的模型或高德/FlyAI 调用。需要检验真实输入时，可在独立会话上传已遮挡敏感信息的当前有效订单截图，解析后补全必要参数；实时工具核验须在构建后显式执行，受公开站点费用额度限制。

应用也可本地复现：按 README 创建并激活项目虚拟环境，安装固定版本依赖并配置自己的凭据，运行 `python app.py`，访问 `http://127.0.0.1:7860/`。仅体验公开功能示例无需自行配置云端凭据。

## 踩坑记录（可选）

- 普通车票往往不包含整趟旅行预算或同行约束，因此不再用演示行程补空，而是生成待确认草稿，要求用户补齐必要信息。
- 车票截图中的酒店广告、下单日期和退票状态不能混成有效行程；解析提示与校验分别处理这些情况。
- 高德结果可能只有行政区坐标，天气也可能未覆盖出行日期；精度或覆盖不足时保留未核验状态，不编造结论。
- 大模型输出的候选需与实际工具返回的名称、链接、单一价格绑定，再进行预算和风险复检。
- 新版 Gradio 聊天组件使用文本块列表，原来的字符串过滤会丢掉历史回答；已补充真实组件格式回归测试，同时修复历史自动切换和本地重启换钥问题。
- 多图汇总曾遗漏一张车票，导致引擎只检查剩余单段并显示 0 风险。修复重点不是硬加一个风险，而是逐图返回、覆盖校验和程序合并；旧多图会话缺少覆盖记录时要求重新解析，不沿用原来的无风险结论。

## 产品边界与后续价值

本版本是可公开体验的行程核对与辅助决策工具，不是自动预订、支付或退改系统。用户仍需自行确认库存、最终价格、退改规定和实际订单状态。历史按浏览器隔离，不提供跨设备账户同步；原图临时清理，浏览器仅保留小尺寸预览和已解析内容。网页不为每位用户后台自动定时巡检。

应用通过问答缓存、本地规则与每日调用额度控制公开体验成本；额度不是匿名用户的强身份认证，也不是云账单的硬止损。商业化方向可从旅行前订单核对、家庭约束检查和行程变更辅助切入，但尚未验证付费意愿、用户规模或商业收入，不虚构这些数据。

后续可围绕旅行前订单核对、行中变更提醒和家庭出行约束持续优化，并探索与旅行平台售后或行中服务结合；这些属于演进方向，不宣称已经上线或获得商业验证。

项目使用 AI 编程辅助完成部分代码、测试与文档；作者负责场景选择、产品决策、平台配置、实际验收和最终提交。
